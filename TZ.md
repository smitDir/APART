# ТЗ и архитектура: Tvoy Apart 24/7 — система бронирования

## 1. Контекст

- Лендинг: `index.html`, размещён по адресу `radegust.ru/lending/apart/` (путь на существующем хостинге).
- Сейчас 1 объект: студия 11 м², Чистые Пруды. План — добавлять новые объекты.
- Форма брони на лендинге сейчас никуда не отправляется (нет backend).

## 2. Решения по архитектуре

| Вопрос | Решение |
|---|---|
| Масштаб | Мультиобъектная модель данных с самого начала (`property_id`), даже при 1 объекте сейчас |
| Подтверждение брони | Автоматически, по вебхуку об успешной оплате ЮKassa |
| Календарь занятости | Да, на лендинге — виджет на vanilla JS, тянет занятые даты с API |
| Оркестратор | Свой лёгкий backend (Node.js/Express), без n8n — меньше движущихся частей для CRUD + webhook-логики |
| БД | MySQL/MariaDB на VPS — своя база на каждый проект/направление (не общая), по решению пользователя |
| Домен | Лендинг остаётся на `radegust.ru/lending/apart/`; API — отдельный домен `apart247.ru` на VPS, не поддомен radegust.ru |
| Уведомления | Telegram Bot API напрямую (HTTP-запрос), опционально email по SMTP |

## 3. Модель данных

**properties**
- id, name, address, description, capacity, base_price, active

**bookings**
- id, property_id, full_name, phone, email, check_in, check_out, guests, children, purpose, payment_method, services (JSON-массив), comments, status (`pending` / `paid` / `confirmed` / `cancelled`), yookassa_payment_id, created_at

Занятость объекта = диапазоны дат броней со статусом `paid`/`confirmed`, пересекающиеся по датам. Отдельная таблица календаря не нужна — считается запросом.

## 4. API

- `GET /api/properties` — список объектов
- `GET /api/properties/:id/availability?from=&to=` — занятые диапазоны дат
- `POST /api/bookings` — создать заявку; проверяет конфликт дат; если `payment=link` — создаёт платёж в ЮKassa и возвращает `confirmationUrl`
- `POST /api/webhooks/yookassa` — приём уведомления об оплате; проверка подписи/IP; перевод брони в `confirmed`; уведомление в Telegram
- `GET /api/admin/bookings` — список броней (Basic Auth), для менеджера

## 5. Развёртывание (после установки VPS)

1. VPS: Ubuntu 24.04, Node.js 20+, MySQL/MariaDB (отдельная база на проект),
   nginx как reverse proxy, certbot для HTTPS.
2. Домен `apart247.ru` → проксирует на `localhost:3000` (порт backend).
3. `.env` с реальными секретами: `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `ADMIN_PASSWORD`, `DB_*`.
4. Backend как systemd-сервис (`pm2` или `systemd unit`), автозапуск при перезагрузке.
5. В `index.html` заменить `API_BASE_URL` на `https://apart247.ru`.

Решения по новым развилкам:

| Вопрос | Решение |
|---|---|

### 8.1 Клиентский путь через бот

Клиент видит пост в любом канале (Telegram/YouTube) → переходит по ссылке на бота →
1. Бронирование: выбор свободных дат (календарь из того же API, что и на сайте) → подтверждение
2. Доп. услуги: трансфер, завтрак/обед — выбор блюд из меню (хранится в БД, редактируется без правки кода)
3. Оплата: тот же механизм ЮKassa, что и на сайте (единая бронь = единый источник правды)
4. После брони бот выдаёт:
   - Инструкции по бытовым приборам (текст/фото, по объекту)
   - Контакты экстренных служб
   - Подборку мероприятий (музеи/театры/парки/спорт) — статический редактируемый контент
   - Контакт менеджера
5. Согласие на обработку ПД / договор аренды / условия проживания — принимается в боте (кнопка "Согласен"), лог сохраняется в БД на российском сервере

### 8.2 Данные

Новые таблицы: `menu_items` (меню доп.питания, редактируется), `booking_items` (заказанные позиции к брони),
`consents` (лог согласий/договоров: booking_id, тип документа, версия текста, telegram_user_id, дата/время),
`property_content` (инструкции/экстренные контакты/мероприятия по объекту — редактируемый текст),
`scheduled_posts` (очередь постов: подпись, промпт для генерации, статус, канал, время публикации).

Всё хранится в той же SQLite на вашем российском сервере — единая точка хранения данных клиентов и переписки, без выноса за рубеж.

### 8.3 Контент-конвейер (Telegram-канал + YouTube)

1. Генерация фото/видео по объекту через RunComfy (промпт → изображение/видео)
2. Планирование поста (подпись + медиа + время публикации) — таблица `scheduled_posts`
3. Публикация: Telegram Bot API (`sendPhoto`/`sendVideo` в канал) — работает сразу с токеном бота
4. Публикация на YouTube: требует создания YouTube-канала (уже решено — создаём) и OAuth-доступа к YouTube Data API v3 — появится отдельным шагом после создания канала

### 8.4 AI-продавец (свободный диалог)

По мотивам разбора чужого решения (n8n + Supabase RAG + Postgres memory) приняли решение:
для Apart — не копировать эту инфраструктуру, а расширить уже готового бота разговорным
слоем поверх существующего стека (Node.js/SQLite), без n8n/Supabase/отдельного Postgres.

- LLM: Google Gemini (бесплатный тариф, `GEMINI_API_KEY`) — выбран как оптимальный
  бесплатный вариант с хорошим качеством на старте проекта
- База знаний: не векторная — весь текст (`property_content`, `menu_items`) целиком
  идёт в системный промпт; для одного объекта этого достаточно, RAG избыточен
- Память диалога: таблица `chat_messages` (по chat_id, последние 20 сообщений)
- Эскалация к менеджеру: кнопка «Написать менеджеру» на каждом AI-ответе

Связка n8n + Supabase (вектор. БД) + Postgres из разобранного видео — отложена
как отдельный переиспользуемый шаблон для БУДУЩИХ клиентских проектов с большой
базой знаний (не для Apart), когда будет готов VPS.

### 8.5 Черновики пользователя (BPMN), учтены как задел

**Схема "Бот видео"**: форма запроса на видео (админ) → преобразование в промт →
обогащение промта требованиями к видео → генерация нейросетью → модерация
админом (можно публиковать? да/нет) → сохранение в хранилище → публикация на
YouTube. Почти совпадает с уже реализованным конвейером (`scheduled_posts`),
не хватает: (1) явного шага обогащения промта шаблоном/брендгайдом,
(2) формального статуса модерации (сейчас `generated`/`posted` без
explicit approve/reject).

**Схема "Телеграм-бот"**: самообучающаяся база знаний. Бот ищет ответ в базе
знаний → если не найден — вопрос уходит админу в личный Telegram → админ
отвечает → пара вопрос/ответ сохраняется в базу знаний для будущих
аналогичных вопросов. Это дополняет наш AI-слой (сейчас неизвестный вопрос
просто получает кнопку "менеджер" без сохранения ответа для повторного
использования) — стоит добавить таблицу `faq_entries` + поток эскалации
конкретному человеку с сохранением ответа обратно в базу.

Не реализовано, ждёт решения — делать сейчас или после VPS.

### 8.6 Черновик "Полный цикл проживания" (3-я BPMN-схема)

Самая подробная схема — весь путь гостя от входа (сайт или ТГ) до закрывающих
документов. Вводит несколько элементов, которых нет в реализованном пока
функционале:

- **Паспортные данные при подписании оферты** — аннотация на схеме: "подписание
  договора, паспортные данные, контакты, способ общения". Это больше, чем наше
  текущее "простое согласие" — нужно решить, собираем ли паспортные данные
  (для договора аренды) отдельным полем, и как/где их храним (это уже
  персональные данные повышенной чувствительности — вопрос защиты по 152-ФЗ
  становится более предметным).
- **QR-код на оплату** — аннотация: "Настроить в юкассе варианты оплаты".
  ЮKassa поддерживает СБП (Систему Быстрых Платежей) через QR — сейчас у нас
  только редирект на страницу оплаты, QR не реализован.
- **Роль "уборщик"** — отдельный адресат Telegram-уведомлений (сообщения о
  подготовке объекта к заезду и уборке после выезда), которого у нас пока
  вообще нет в модели (только "менеджер"/админ).
- **Отмена после оплаты** — если гость не заехал (таймер ожидания на этапе
  "ОЖИДАНИЕ ЗАЕЗДА"): снятие брони с календаря + уведомление админу +
  частичный возврат средств. У нас пока нет логики отмены/возврата вообще.
- **Таймеры заезда/выезда** — фоновые события по времени (напоминания об
  уборке, окончание срока проживания) — это классическая задача для cron/
  планировщика, а не для чат-бота как такового.
- **Закрывающие документы** — акт/документы после выезда, отправляются гостю.
- **Отчёт о неисправностях** — уборщик/админ сообщают о состоянии/поломках
  после выезда гостя.
- **Открытый вопрос от вас самих** ("КАК?" на схеме, у шага "Авторизация и
  аутентификация" на сайте) — вы сами отметили это как нерешённое: как именно
  должна работать авторизация на сайте (нужна ли она вообще для бронирования,
  или это про личный кабинет постоянного гостя). Не реализовано, ждёт ответа.

Не реализовано, ждёт приоритизации — это большой пласт (роль уборщика,
таймеры, отмена/возврат, документы) поверх уже готового MVP бронирования.

### 8.9 Бюджетная альтернатива по сигналу "дорого"

Основной путь бронирования — студия (`/book` по умолчанию). Бот сам предлагает

### 8.10 Контент-план: еженедельное предложение постов (п1 из полного цикла)

Решение по разделению труда: маркет-исследования/сценарии — моя (Claude) работа
в сессиях по расписанию (еженедельно первые 2 месяца, далее ежемесячно), а не
отдельная автономная система на VPS. Пользователь задаёт тему на месяц и ссылки
на официальные городские мероприятия — я делаю обзор/сценарии на их основе.

Реализовано:
- `content_themes` — тема месяца (`month`, `theme`, `notes`)
- `scheduled_posts` расширен: `content_type` (text/photo/video), `theme`, `week_of`
  — пакетное предложение постов на неделю вместо одного поста за раз
- `POST /api/admin/posts/week` — создать пакет; `GET .../week/:weekOf` — посмотреть;
  `POST .../week/:weekOf/approve` — утвердить пакетом
- Первый пакет (неделя 2026-07-06, тема "История и мистика Чистых Прудов")
  создан и утверждён как пример — часть постов сознательно использует уже
  существующее реальное фото сайта (`vhodzakrt.jpg`), а не выдуманные
  исторические факты о конкретном здании

**"Карусель" — уточнено**: это рекламная методика (последовательность слайдов:
хук → детали → призыв к действию), не формат конкретной площадки. Реализовано
как `content_type: 'carousel'` в `scheduled_posts` — `media_path` хранит
JSON-массив путей вместо одного пути, публикуется через Telegram media group
(`bot.sendMediaGroup`, свайпается как альбом). Подпись показывается только у
первого элемента (так работает сам Telegram). Проверено локально (мок
`sendMediaGroup`) — корректно определяет фото/видео по расширению, подпись
только на первом элементе.

**Правила размещения рекламы (РФ)**: платное размещение у сторонних
каналов/блогеров требует `erid`-маркировки через ОРД. Собственные посты на
своём канале о своих же услугах под это не подпадают. Пользователь
самостоятельно уточняет вопрос про "#реклама" на постах взаимного пиара —
не реализовано, ждёт его решения, не мой вопрос для code review.

**Отложено на месяц (по решению пользователя)**: "Создание видеороликов" (агенты
для сценариев/маркет-исследований по вирусным роликам, монтаж) — п2 полного
цикла, начинаем через месяц после п1.
